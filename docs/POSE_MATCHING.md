# Incremental multi-view face matching

Indexing can consult up to six diverse references per person, in addition to its quality-weighted centroid. References require quality >=0.55 and detector confidence >=0.85. Cosine >=0.98 views are deduplicated, retaining the better-quality example. Reference search uses the existing local FAISS exact inner-product runtime, with a NumPy fallback; dirty people are handled incrementally and the bounded reference index rebuilds with the existing centroid index. References reconstruct from authoritative stored embeddings on cache invalidation/restart; no embedding migration or re-inference is required.

For a query with quality >=0.5 and confidence >=0.85, reference rescue needs two diverse supporting views at cosine >=max(0.60, configured matching threshold+0.12), plus centroid agreement >=max(0.30, threshold-0.10). The second-best supporting score is used. These conservative parameters are provisional, not calibrated accuracy claims. Exclusions, rejections, separation constraints, co-occurrence and ambiguity checks still apply. With an active learned matching model, reference rescue is disabled to preserve its original centroid-score feature contract; it requires separate validation before changing that contract.

Track matching now supplies the selected best-quality leader's face metadata along with its embedding, rather than the first chronological member's metadata. Source coordinates and frame records remain intact. Existing people are not automatically merged. This reduces new fragmentation when adequate reference evidence exists, but cannot guarantee all poses match or repair already split identities. Synthetic tests verify supported pose rescue, single-view rejection, repeated-frame deduplication, bounded storage, low-quality rejection, exclusion, co-occurrence and reference reconstruction.

## Video publication cache correction

Publication now processes each track's best face first and then its members before assigning the next track. Previously only track leaders updated the live matching cache; accepted members were visible to matching only after the entire video finished. A later segment could therefore create a new person despite useful evidence already being present in the video's earlier track. Each accepted new member now updates the centroid cache, bounded pose references and same-video identity memory immediately. The final database refresh remains authoritative. This uses existing embeddings and leaves the configured matching threshold unchanged.

Propagation to a track member independently checks face rejection, media exclusion and same-frame co-occurrence, in addition to the existing embedding/learned matching gates. Existing leaders seed the track assignment during retry so an unassigned member's rejection cannot be bypassed through its already-assigned leader. Existing assigned/manual faces are preserved.

The publication regression reproduced two failures against the previous implementation: a synthetic identity split into two people after a pose change, and two simultaneous faces sharing one person. Both pass with the correction; an unrelated synthetic identity remains separate. Additional tests cover stable face IDs and preserved manual reassignment/rejection on republication. This demonstrates those bugs are fixed; it is not a measured real-library accuracy score. Already-published fragmented profiles retain their IDs and still require a separate, user-confirmed correction.

Validation on 2026-10-12: matching/checkpoint suite 52 passed; publication/manual-correction/library/video suite 16 passed (two longer tests deselected in that invocation). The real-model two-person video test was then executed separately on both CPU (1 passed) and CoreML (1 passed). It checks two identities across exits/re-entry, person moments and generated clip boundaries. CoreML remained the active provider at 640 px after the full test. No production data was reset, merged or used for write experiments by these tests. The user separately reset their live library during implementation, so the screenshot's old IDs were no longer available for repair.
